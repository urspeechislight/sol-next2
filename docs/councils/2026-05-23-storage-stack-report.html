sol-next2 storage stack

Five advisors. Five peer reviews. One chairman. Question: Postgres + pgvector vs Neo4j vs SQLite vs the proposed four-store stack for a read-only reader over the sol-next pipeline's output.

Chairman's verdict

Where the council agrees

Four of five advisors reject the proposed four-store stack (Postgres + Neo4j + Qdrant + Redis) as operational overkill for a single-dev, self-hosted, read-mostly workload against a corpus that doesn't yet exist in materialized form. Only the Expansionist defends complexity, and that defence is product vision dressed as architecture.

On the graph side, three independent lines of attack reach the same destination: AGE's planner is unreliable for variable-length paths (Contrarian); recursive CTEs run in milliseconds at this scale (Executor); the workload isn't graph-shaped at query time — isnad chains are pre-materialized paths inside each hadith document (First Principles).

On vectors: defer until a real user complains; pgvector is sufficient until it isn't. Qdrant has no organic advocates.

Where the council clashes

SQLite vs Postgres in production. First Principles says SQLite read-only is correct because the workload is artifact distribution. Executor says skip SQLite — pgvector and proper FTS push you to Postgres and you'd migrate twice. Contrarian dismisses SQLite as "suicidal at thousands of books." The disagreement is real because they're sizing for different futures.

Arabic FTS in Postgres. Contrarian is the only advisor who treats classical-Arabic tokenization (tashkeel, ta marbuta, root stemming) as a first-class concern and concludes Postgres tsvector is inadequate without significant custom work. Two reviewers caught this gap in the others.

Whether to plan for scale at all. Outsider and First Principles say no — working set is ~100k rows, "eventually" is hypothetical, ship for what exists. Executor says ship Postgres now because migration cost beats premature optimization. Expansionist says scale is the point. The data is on the no-side: 30KB today, an unrun pipeline upstream, zero users.

Blind spots only peer review caught

Four of five reviewers independently flagged the same gap no advisor addressed: the upstream contract. None of the advisors asked what sol-next actually emits. If upstream writes Postgres dumps and Neo4j exports, rejecting them means maintaining an ETL layer forever. If it emits Parquet or JSONL, First Principles' artifact model is trivial. The SSOT question isn't "which database" — it's whether sol-next2's store is the SSOT or a derived view.

Reviewers also flagged:

  • Embedding pipeline lifecycle — model choice owns re-embedding millions of records on every swap.
  • Arabic-specific normalization — narrator name variants (kunya/nasab/laqab) belong to sol-next, not sol-next2.
  • Citation stability — Bukhari numbering, Shamela vs printed editions: the real SSOT problem hiding behind the storage question.

Recommendation

Adopt the First Principles architecture, modified by the reviewer-caught blind spot.

Concretely: sol-next2 reads a single canonical artifact emitted by sol-next. Default to SQLite with FTS5 + sqlite-vec + JSON1, opened read-only by FastAPI, with NetworkX in-process for the rare narrator-traversal. The artifact is versioned, immutable, atomically swapped on republish.

Carve-outs:

  • Validate SQLite FTS5 with a custom classical-Arabic tokenizer against real queries. If it fails the Contrarian's tashkeel/root-stem test, add Meilisearch as a derived index — rebuilt from the canonical artifact, never a second SSOT.
  • Postgres is the escape hatch, not the default. The day a user complains about something SQLite + adjacency lists can't do, swap. Migration from a versioned read-only artifact to Postgres is a day's work, not a rewrite.

Executor's "just ship Postgres" is the acceptable second-best if there's zero appetite for the artifact model. Expansionist's stack is wrong for the stated problem.

The one thing to do first Negotiate the sol-next output contract. Define one canonical, versioned artifact (SQLite file or Parquet bundle) that sol-next2 consumes as immutable input. Every downstream storage decision becomes a derived-view problem instead of an SSOT problem. Do this before writing a line of sol-next2 storage code.

Advisor responses (full)

The First Principles Thinker (chairman's pick)

It's a build-artifact problem, not a database problem.

sol-next2 serves an immutable, append-rarely, read-mostly corpus that another pipeline has already computed. That is not a database problem; it is a build-artifact distribution problem.

Is the graph actually graph-shaped? No. Narrator chains are paths already materialized inside each hadith document — you read them, you don't traverse them. "Commentaries citing a hadith" is a reverse-index dict. "Parallels" is the same. 1–5 hop narrator traversal at tens of thousands of nodes fits in RAM as an adjacency list — NetworkX in-process beats Neo4j over the network.

The 8 access patterns collapse to 3 primitives: key/ordered lookup, inverted indexes, vector ANN.

Minimum stack: a single SQLite file with FTS5 + sqlite-vec + JSON1. FastAPI opens it read-only. Postgres/Neo4j/Qdrant/Redis assume mutability and concurrent writers you don't have — they are correct for sol-next (the pipeline), wrong for sol-next2.

The real question isn't "which 4 stores" — it's "why are you running any servers for a read-only artifact?" Ship a file. Version it. Mount it.

The Contrarian

Three stores. Each doing what it's good at.

Apache AGE is a trap. Slow releases, uncertain PG18 story, partial openCypher, planner that doesn't understand graph cardinality. For 1–5 hop traversal at scale you'll hit planner pathologies on variable-length paths. Write CTEs from day one, or use Neo4j — don't pretend AGE is real.

pgvector at millions with multilingual embeddings: HNSW build on 5M × 1024-dim is hours; no zero-downtime rebuild without orchestration. Filtered vector search scoped by book/grade — pgvector's pre/post-filter behaviour is ugly. Qdrant handles payload filtering natively.

Postgres tsvector default Arabic is mediocre — no root-based stemming, no tashkeel handling, no ta marbuta normalization. Pattern 5 will feel broken to Arabic readers. Custom dictionary, pg_trgm gymnastics, or OpenSearch/Meilisearch.

SQLite as read-mirror: fine for 8 books, suicidal at thousands. Skip.

Position: Postgres + Neo4j + Meilisearch/ OpenSearch. Defer vectors until pattern 6 has a real user.

The Executor

Keep JSON. Postgres later. Docker-compose, one service.

Monday morning, nothing new. Keep shipping JSON. The upstream pipeline hasn't been run on the full corpus. You don't have a Postgres dump, a Neo4j export, or a Qdrant collection. Picking a stack now is choosing furniture for a house that hasn't been built.

When sol-next produces real output: docker compose up postgres. One container, one backup (pg_dump | zstd | rclone), one CVE channel.

  • pgvector over Qdrant — until >10M vectors, separate vector DB is a second daemon at 2am.
  • Recursive CTEs — not Neo4j/AGE/Memgraph. 1–5 hops on tens of thousands of nodes is WITH RECURSIVE in ms.
  • One store: Postgres. tsvector, pgvector, CTEs, UNLOGGED tables (or skip Redis entirely until cache misses matter).
  • Skip SQLite — pgvector and proper FTS push you to Postgres anyway. Don't migrate twice.

One service. One cron. One apt. Ship.

The Outsider

"Eventually" is doing all the work.

The gap between "today: 8 books, 1 sample page, 30KB of JSON" and the elaborate four-database stack being proposed is the actual story. Thirty kilobytes. You're picking a five-engine setup for a go-kart.

The classical hadith corpus across all major collections is roughly 50,000–100,000 unique narrations. Where are the millions coming from? Translations and variants — that's denormalization you're choosing.

Does a human user actually traverse 5 hops of narrator chains? 95% never click past hop 1 or 2. Recursive descent is still a tree — Postgres recursive CTEs eat it.

Vector "related" — has anyone clicked it? Nobody has used this product. You're sizing infrastructure for hypothetical usage.

Ship Postgres. One database. Add pgvector when a user complains. Add graph the day a real query needs it. You will almost certainly never reach that day.

The Expansionist

Consolidation unlocks compounding moves.

Postgres + pgvector + Apache AGE. One database — not for "fewer moving parts" but because consolidation is what unlocks the compounding moves. You're building the first queryable graph-vector index of the classical hadith corpus in English.

What one Postgres unlocks:

  • Hybrid queries in single SQL — "semantically similar to X, through Bukhari's teachers within 2 hops, sahih, ≥3 citations" — one CTE + AGE traversal + pgvector + FTS.
  • Isnad-aware retrieval API — chain credibility weighted by narrator graph centrality.
  • Narrator disambiguation as a service.
  • Provenance-traced LLM grounding (MCP server).
  • Parallel-hadith discovery as research contribution.

Skip SQLite, Neo4j licensing tax, Qdrant duplication. The constraint isn't operational — it's imaginative.

Reviewer consensus marked this as the council's biggest blind spot: a startup pitch, not an engineering answer. Hand-waves AGE's planner immaturity (Contrarian's substantive concern) and Arabic FTS quality. Builds for users that don't exist.

Peer-review highlights

What every reviewer agreed on

All 5 reviewers independently ranked the First Principles response strongest, citing the same three reasons:

  • It was the only response that interrogated the shape of the workload instead of pattern-matching on "graph + vector + multilingual."
  • Correctly identified sol-next2 as a build-artifact distribution problem, not a database problem.
  • The collapse of 8 access patterns into 3 primitives (key/ordered lookup, inverted indexes, vector ANN) is the kind of reduction that prevents months of wasted ops work.

All 5 reviewers flagged the Expansionist response as the biggest blind spot — selling a vision rather than answering the question, hand-waving the Contrarian's substantive technical objections (AGE planner, Arabic FTS quality), building for users that don't yet exist.

What every advisor missed (caught only in peer review)

The upstream contract. Four of five reviewers independently flagged that no advisor asked what sol-next actually emits. If sol-next writes Postgres/Neo4j/Qdrant snapshots, rejecting them means maintaining an ETL layer forever. The SSOT question isn't "which database" — it's whether sol-next2's store is the SSOT or a derived view.

Embedding pipeline lifecycle. Whoever picks the multilingual classical-Arabic embedding model owns re-embedding millions of records on every model swap. That belongs upstream.

Narrator-name normalization. Kunya/nasab/laqab variants are a data-quality concern that constrains every downstream store choice. Belongs to sol-next.

Citation stability. Bukhari numbering, Shamela vs printed editions — the real SSOT problem hiding behind the storage question.
